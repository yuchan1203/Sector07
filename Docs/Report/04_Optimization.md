# 3단계: 프로젝트 최적화 (2026-11-02)

## 1. AI가 제안한 최적화 방법 (후보 목록)
AI에게 CPU, GPU, RAM 관점의 최적화 방법을 묻고, **이 프로젝트에서 실제로 측정한 값**을 근거로 후보를 골랐어요.

| 분류 | AI 제안 항목 | 이 프로젝트에서 확인한 사실 | 선택 |
|---|---|---|---|
| GPU | 고폴리곤 모델 정리 / LOD | 플레이어 모델(`Model_Meshy/Mesh_0`)이 **삼각형 22만 개 Skinned Mesh**인데, 1인칭에서도 그려져요 | ✅ |
| GPU | 서브 카메라 렌더링 비용 줄이기 | 미니맵 카메라가 Far 1000, **그림자를 켠 채** 씬 전체를 한 번 더 그려요 | ✅ |
| GPU | 그림자 / Shadow Distance | 조명 단계에서 Shadowmask로 이미 처리했어요 (그림자 캐스터 329→80) | (완료) |
| GPU | SSAO 등 포스트 프로세싱 | 포스트 프로세싱 단계에서 이미 처리했어요 (SSAO 메모리 -29MB) | (완료) |
| GPU | Occlusion Culling | 베이크하지 않았어요. 공장 건물이 많아 효과가 있을 수 있어요 | ❌ 시간 관계상 제외 |
| RAM | 텍스처 Max Size / 압축 | 손에 든 작은 검이 **2048 텍스처 4장(32MB)**을 써요 | ✅ |
| RAM | 폰트 아틀라스 | 데미지 숫자(0~9)만 쓰는 폰트가 **한글 11,267자 4096x4096 아틀라스(32MB)**예요 | ✅ |
| RAM | 오디오 Load Type, 모델 Read/Write | 측정상 상위 항목이 아니었어요 | ❌ |
| CPU | 오브젝트 풀링 | 총알 피격 이펙트, 데미지 텍스트, 핏자국을 매번 `Instantiate`/`Destroy`해요 | ✅ |
| CPU | Update 최적화 / 캐싱 | 평소 GC Alloc은 프레임당 약 20KB로 낮고, Main Thread도 대부분 에디터 비용이에요 | ❌ 효과가 작음 |

> AI의 일반론("Update를 줄여라" 등)을 그대로 적용하지 않고, **측정해서 비용이 큰 곳부터** 골랐어요. 예를 들어 CPU 쪽은 평소 부하가 낮아서 Update 최적화는 효과가 거의 없을 것으로 판단했어요.

측정 조건은 앞 단계와 같아요: 에디터 Play 모드, 1920x1080, 게임을 Ready로 고정해 정지 상태로 측정. 출발점은 포스트 프로세싱 최종 상태예요.

## 2. GPU: 1인칭 몸 숨기기 + 미니맵 카메라 정리

### 적용 내용
1. **1인칭에서 플레이어 몸을 그림자로만 그리기** (`CameraViewSwitcher.cs`)
   - `_firstPersonHiddenRenderers`(Mesh_0, Sword1_Silver)를 추가했어요.
   - 시점이 FirstPerson일 때 `ShadowCastingMode.ShadowsOnly`로 바꿔요. 화면에는 안 그리지만 그림자는 그대로 남아요.
   - 다른 시점으로 바꾸면 다시 `On`으로 돌아가요 (3인칭에서 몸이 보이는 것 확인: `Opt/final_thirdperson.png`).
2. **미니맵 카메라 정리** (씬 설정)
   - 그림자 렌더링을 껐어요. 위에서 내려다보는 아이콘 지도라 그림자가 필요 없어요.
   - Far Clip Plane을 1000에서 30으로 줄였어요. 카메라가 플레이어 위 10m에 있으므로 30m면 충분해요.
   - 플레이어 모델 레이어를 Default에서 **Player**로 바꿨어요. 미니맵 Culling Mask에 Player가 없어서 22만 폴리곤 모델이 미니맵에서 빠지고, 미니맵에는 원래대로 `MinimapIcon`이 표시돼요.
   - 확인: 총 Raycast는 원래 Player 레이어를 제외하고, 모델에는 Collider가 없어서 게임 로직에 영향이 없어요.

### 결과
| 지표 | Before | 1인칭 몸 숨김만 | + 미니맵 정리 (최종) | 변화 |
|---|---|---|---|---|
| **Triangles** | 250만 | 162만 | **94만** | **-63%** |
| **Batches** | 281 | 275 | **204** | **-27%** |
| SetPass Calls | 73 | 71 | 62 | -15% |
| **Shadow Casters** | 81 | 80 | **10** | **-88%** |
| FPS | 125.3 | 125.4 | 125.4 | 같음 |

### 분석
- **1인칭 몸 숨김:** 화면에 안 보이는 22만 폴리곤을 메인 카메라가 매 프레임 그리고 있었어요. 삼각형 88만 개가 줄었어요(SSAO 깊이 프리패스에서도 함께 그려지고 있었음).
- **미니맵 그림자 끄기:** 효과가 가장 컸어요. URP는 **카메라마다 그림자 맵을 따로 렌더링**해요. 그래서 미니맵 카메라가 그림자 패스를 통째로 한 번 더 돌리고 있었어요. 이걸 끄자 그림자 캐스터가 80에서 10으로 줄었어요.
- **FPS는 그대로예요.** 앞 단계와 같이 에디터의 CPU 오버헤드가 병목이기 때문이에요. 하지만 삼각형 -63%, Batches -27%는 GPU가 약한 목표 기기(노트북 내장 GPU, 모바일)에서는 프레임 시간에 직접 반영돼요.

## 3. RAM: 텍스처 크기 + 폰트 아틀라스

### 적용 내용
1. **검 텍스처 Max Size를 2048에서 512로** (`Sword1_Albedo_Silver/Normal/Metallic/Emission`). 손에 든 작은 검이라 화면에서 512 이상의 해상도가 필요 없어요.
2. **데미지 텍스트 폰트 교체** (`Damage.prefab`): `BMKkubulim_2`(4096x4096, 한글 11,267자)를 `BMJUA_2`(2048x2048, UI에서 이미 쓰는 중)로 바꿨어요.
   - 데미지 텍스트는 숫자만 표시하는데, 이를 위해 한글 전체가 들어간 4096 아틀라스를 통째로 메모리에 올리고 있었어요.
   - `BMJUA_2`는 이미 UI용으로 로드돼 있어서 추가 비용이 없어요. `BMKkubulim_2`는 더 이상 아무도 참조하지 않아 로드되지 않아요 (GUID 참조 검색으로 확인).
   - **대가:** 데미지 숫자의 글꼴 모양이 바뀌어요. 디자인상 원래 폰트가 꼭 필요하면 되돌리고, 원본 TTF로 숫자만 담은 작은 아틀라스를 새로 만드는 것이 대안이에요(현재 프로젝트에는 원본 TTF가 없음).
3. 시도했다가 포기한 것: **한글 UI 폰트(`펀플로 생존자_6`, 4096)를 Dynamic 아틀라스로 바꾸기.** 원본 TTF 파일이 프로젝트에 없어서 아틀라스를 다시 만들 수 없었어요.

### 결과 (로드된 프로젝트 텍스처의 메모리 합계)
측정 방법을 바꿨어요. 전체 `Texture Memory` 카운터는 에디터에서 ±10MB씩 흔들려서, 로드된 텍스처 에셋을 하나씩 `Profiler.GetRuntimeMemorySizeLong`으로 재서 합산했어요.

| 지표 | Before | After | 변화 |
|---|---|---|---|
| **로드된 텍스처 합계** | **211.9 MB** | **149.9 MB** | **-62.0 MB (-29%)** |
| 그중 TMP 폰트 아틀라스 | 72.0 MB | 40.0 MB | -32.0 MB |
| 검 텍스처 4장 | 32.1 MB | 약 2 MB | 약 -30 MB |

- 에디터에서는 폰트 아틀라스가 CPU 사본까지 2배(16MB→32MB)로 잡혀요. 빌드에서 실제로 아끼는 양은 폰트 약 16MB, 검 텍스처 약 15~30MB예요.
- 에디터는 한 번 열었던 에셋을 계속 들고 있어서, 처음엔 바꾼 뒤에도 옛 폰트가 메모리에 남아 있었어요. `Resources.UnloadUnusedAssets()`를 호출한 뒤에야 빠졌어요. **에디터 메모리 측정은 캐시 영향을 받으니 주의해야 해요.**

## 4. CPU: 오브젝트 풀링 (+ 핏자국 누수 수정)

### 문제 발견
- 피격 1회마다 `Instantiate`를 3번 해요: 총알 피격 이펙트, 데미지 텍스트, 핏자국.
- 그런데 **핏자국 이펙트(`BloodSprayFX`)가 반복 재생(loop)이고 삭제 코드도 없어서, 맞을 때마다 좀비에 붙어 영원히 남아요.** 좀비가 오래 살아 있으면 계속 쌓이는 **누수**예요.

### 적용 내용
- `Manager/PoolManager.cs`(새 파일): `UnityEngine.Pool.ObjectPool`로 프리팹별 풀을 관리해요. `PoolManager.Spawn(prefab, 위치, 회전, 부모, 수명)`.
  - 쉬는 오브젝트는 **비활성 부모(Inactive) 아래**에 둬서, 생성 순간이나 대기 중에는 `Awake`/`OnEnable`/`Update`/렌더링이 돌지 않아요.
  - 스스로 Destroy되는 파티클(Stop Action = Destroy)은 생성할 때 Callback으로 바꿔서 풀로 돌아오게 해요.
  - `DontDestroyOnLoad`를 쓰지 않아 씬을 다시 불러오면 풀도 함께 초기화돼요(`GameManager.Restart` 대응).
- `Manager/PooledObject.cs`(새 파일): 자신을 풀로 돌려보내요. 수명 타이머, 파티클 종료 콜백, `ReleaseOrDestroy`(풀 오브젝트가 아니면 기존처럼 Destroy)를 처리해요.
- 바뀐 호출부:
  - `HitscanWeapon.PlayHitEffect`: `Instantiate`를 `PoolManager.Spawn`으로 바꿨어요.
  - `Zombie.TakeDamage`: 데미지 텍스트와 핏자국을 `PoolManager.Spawn`으로 바꿨어요. 핏자국은 `_bloodSprayDuration`(1초) 뒤에 풀로 돌아가요. **누수가 사라지고, 피를 뿜는 연출은 1초로 바뀌어요.**
- 재사용 대응:
  - `Mover`: `Destroy`를 `PooledObject.ReleaseOrDestroy`로, `OnEnable`에서 시간을 초기화해요.
  - `DamageTextEffect`: `Start`를 `Awake`(기본 크기 저장)와 `OnEnable`(위치 흩뜨리기, 크기 초기화)로 나눴어요.
  - `ShakeCameraOnce`: `Start`를 `OnEnable`로 바꿔서 재사용할 때도 카메라가 흔들려요.

### 측정 방법: 부하 테스트
평소에는 사격이 없어서 차이가 안 보여요. 그래서 **한 프레임에 30발 피격**(피격 이펙트 30개 + `TakeDamage` 30회)을 일으키는 테스트를 만들었어요. 그 구간의 시간을 `Stopwatch`로 직접 쟀고, 5번 반복했어요(첫 번째는 워밍업).
- 기존 방식(OLD)은 원래 코드와 똑같이 `Instantiate`하는 경로를, 풀링(POOL)은 실제 바뀐 코드 경로를 실행했어요. 같은 Play 세션에서 둘 다 측정했어요.

| 지표 | 기존 (Instantiate) | 풀링 | 변화 |
|---|---|---|---|
| **30발 처리 시간 (워밍업 후 평균)** | **약 20.2 ms** (18.7~21.5) | **약 2.2 ms** (2.20~2.54) | **약 -89%** |
| 30발당 Mono 힙 증가 | +120~124 KB (매번) | +0 KB (워밍업 이후) | 할당 없음 |
| GameObject 수 (버스트 반복 시) | 1362 → 1530 → 1605 → 1812 (계속 증가) | 1122에서 고정 | 재사용 확인 |
| 좀비에 남은 핏자국 | 30 → 60 → 90 → 120 → 150 (누적) | 최대 30 (1초 뒤 회수) | 누수 해결 |

**피격 후 평소 프레임** (5번 버스트 직후, 정지 상태로 약 7초 측정)
| 지표 | 기존 (핏자국 150개 누적) | 풀링 | 변화 |
|---|---|---|---|
| FPS | 100.3 | 114.2 | +14% |
| Main Thread | 9.79 ms | 8.49 ms | -1.3 ms |
| Batches | 613 | 307 | -50% |
| SetPass Calls | 234 | 73 | -69% |

### 분석
- **30발 = 20ms라는 건 기존 방식에서 샷건이나 연사로 많이 맞히는 순간 프레임 하나를 통째로 놓친다는 뜻이에요** (60FPS 기준 한 프레임 16.6ms). 풀링 후에는 2.2ms라 끊김이 사라져요.
- 풀링의 첫 버스트(워밍업)는 27.8ms로 오히려 느렸어요. 풀이 비어 있어 새로 만드는 비용과 `PoolManager` 생성 비용이 겹치기 때문이에요. 로딩 중에 미리 만들어 두는 Prewarm을 추가하면 해결할 수 있어요(미적용).
- 평소 프레임 개선(FPS +14%, SetPass -69%)은 풀링 자체보다는 **핏자국 누수 수정** 덕분이에요. 반복 재생 파티클 150개가 각각 렌더링(SetPass)과 시뮬레이션(CPU)을 먹고 있었어요.
- 피격 후에도 Batches가 정지 상태(204)보다 높은 307인 것은, 피격된 좀비가 **상태 색을 MaterialPropertyBlock으로 바꾸면서** SRP Batcher로 묶이지 않기 때문이에요. 다음 최적화 후보예요.
- Mono 힙 측정(`GetMonoUsedSizeLong`)은 단위가 거칠어서 정확한 바이트 수가 아니라 **"매번 늘어나는가 / 안 늘어나는가"**를 보는 용도로만 썼어요.

위 표는 게임을 정지 상태로 고정해 잰 값이에요. 직접 플레이하며 찍은 Stats는 수치가 꽤 달라요.

- **차이의 원인:** 플레이 중에는 좀비가 움직이고 공격받아서 피격 이펙트(파티클 3개), 핏자국(파티클 3개), 데미지 텍스트가 동시에 수십 개씩 살아 있어요.
  - 파티클과 TMP 텍스트는 각각 따로 그려져서 Batches가 크게 늘어요.
  - 확인 실험: 진행 상태에서 30발 피격 직후 Batches는 233에서 395로, SetPass는 67에서 193으로 늘었어요.

- **새로 드러난 다음 최적화 후보:** 전투 중에는 Batches 대부분을 파티클과 텍스트가 차지해요. 핏자국 이펙트의 파티클 수와 서브 이미터 줄이기, 파티클 GPU Instancing, 데미지 텍스트 수 제한 등이 다음 대상이에요.
- Profiler (`user_profiler_highlights.png`, `user_profiler_timeline.png`):
  - 평균은 Others(에디터) 8.2ms, Scripts 1.7ms, Rendering 0.5ms예요. 조명 단계 캡처와 같은 경향으로, 에디터 비용이 대부분이에요.
  - Timeline에서도 PlayerLoop는 2.17ms이고, EditorLoop가 4.3ms예요.
  - 최대 500ms 프레임과 GC Collect(약 3~5ms)는 에디터 쪽 GC(GC.Finalizer, ReadObjectFromSerializedFile)에서 나온 거예요. 게임 코드의 할당은 상위 항목에 없어요.

## 6. 느낀 점과 한계
- **FPS만 봤다면 "아무것도 안 좋아졌다"고 결론 냈을 거예요.** Profiler로 보니 에디터 비용(EditorLoop)이 프레임의 절반 이상이었어요. 그래서 Batches, 삼각형, 그림자 캐스터, 메모리처럼 **원인에 가까운 지표**를 함께 봐야 했어요.
- **같은 조건으로 측정하는 게 가장 어려웠어요.** 좀비가 움직여서 결과가 흔들렸고, 게임을 정지 상태로 고정하는 방법을 만들어서야 비교할 수 있었어요. 에디터의 에셋 캐시와 GPU 타이머처럼 측정 도구 자체의 함정도 있었어요.
- **"AI가 알려준 대로"가 항상 맞진 않았어요.**
  - 조명 1차 베이크는 오히려 Batches를 늘렸고, Mixed Lighting 모드까지 맞춰야 효과가 났어요.
  - 색감 튜닝도 4번 실패하고 나서야 맞췄어요.
- 가장 큰 개선은 "최적화 기법"보다 **불필요한 일을 찾아내는 것**에서 나왔어요. 안 보이는 몸 그리기, 미니맵의 그림자 패스, 숫자만 쓰는데 올린 한글 폰트, 사라지지 않는 핏자국 같은 것들이에요.
- **한계와 남은 과제**
  - 빌드에서 측정하지 않았어요 (에디터 오버헤드 포함).
  - Occlusion Culling, 플레이어 모델 Mesh LOD, 풀 Prewarm, 좀비 상태 색의 SRP Batcher 호환은 적용하지 않았어요.
